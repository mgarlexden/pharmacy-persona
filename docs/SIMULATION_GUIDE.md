# 시뮬레이션 가이드 — 무엇을, 왜, 어떻게, 그 뒤에

작성: 2026-10-05 초안. 시뮬레이션 담당 구상을 정리한 문서이며 확정 스펙이 아니다.
같이 읽을 것: `docs/HANDOFF.md`(결정 이력), `docs/SERVICE_SCREEN_SPEC.md`(화면), `README.md`(데이터 구조).
이 문서의 근거: 팀 리서치 자료 4건(시뮬레이션 리서치 엑셀, 핵심제안 PDF, 상세구현참고 zip, 의사결정 상황 가정 엑셀)에 대한 검토와 담당자 논의. 확인한 것과 못 한 것은 맨 아래 부록에 적었다.

## 0. 한 장 요약

1. 지금 주장할 수 있는 것은 **"인터뷰 약사 1명(개업 3주차)의 판단을 얼마나 재현하는가"** 뿐이다. 동네 약국 일반의 대변은 주장하지 않는다.
2. 시뮬레이션은 **"조건이 바뀔 때 이 사람의 판단이 어떻게 바뀌는가"** 를 보는 것이다. 상태 계산은 코드, 판단은 LLM, 정답은 실제 약사다.
3. 검증용 시나리오는 **인터뷰에 없던 인접 상황**이어야 하고, 약사와 AI에게 **같은 카드**를 준다.
4. 정보는 **층으로 분리**한다. 인터뷰(개인) / 공공·민간 데이터(장면) / 다른 약사(동료 사전지식)를 섞지 않는다.
5. 판단 재현과 별개로 **니즈·AX 여지**를 보여 준다. 단, 시뮬레이션 출력은 니즈의 증거가 아니라 **가설 후보**다.
6. 최종 목표는 **"의원이 인접한 동네약국 운영자" 유형 페르소나**다. 지금 PoC는 그 방법이 한 사람에게서 작동하는지 확인하는 단계다.

## 1. 이 페르소나는 무엇이고, 무엇이 아닌가

| 말할 수 있다 | 말할 수 없다 |
|---|---|
| 인터뷰 약사 1명의 판단·제약·경험을 근거 ID와 함께 보여 준다 | 동네 약국, 약국 소상공인 일반을 대변한다 |
| 인터뷰에 없던 상황에서 AI 답과 약사 답이 얼마나 비슷한지 비교한다 | 약사 2인(응답자 1명)의 합의·성향을 확정한다 (G07) |
| 가상 수치로 선택의 결과를 계산해 비교한다 (모두 "가상") | 실제 수요·매출·총현금을 예측한다 |
| 어디에 어려움이 있어 보이는지 **가설**로 보여 준다 | 시뮬레이션에서 니즈나 AX 효과를 확인했다고 말한다 |

- 근거는 인터뷰 1건이다. 인터뷰 약사는 개업 3주차이며 같은 건물에 정형외과·이비인후과가 있다(E001, E002). 이는 "의원 인접 약국"이라는 축의 한 점일 뿐이다.
- 인터뷰 약사는 다른 약국 근무 경력이 있다. 이 경력은 전문성의 배경이지만 **과거·타약국 경험**이므로 현재 약국의 판단과 섞지 않는다 (G01).
- 개업 3주차라서 현금 조심성이 **성향이 아니라 개업 초기라는 상태**에서 나왔을 수 있다. 페르소나에는 시점을 표기하고, 몇 달 뒤 달라질 수 있다고 밝힌다.

## 2. 왜 시뮬레이션하는가

두 가지 질문에 답하기 위해서다. 둘은 근거도 검증 방식도 다르므로 섞지 않는다.

| 질문 | 근거 | 확인 방법 |
|---|---|---|
| ① 이 페르소나는 그 약사의 판단을 얼마나 재현하는가 | 인터뷰 + 약사 본인 응답 | 같은 카드에 대한 답 비교 |
| ② 어디에 니즈가 있고 AX 여지가 있는가 | 인터뷰의 자발적 어려움·실제 대처 방식 | 약사가 니즈 카드를 확인 |

**시뮬레이션의 구성 (세 가지)**

1. **세계 상태 전이 (코드):** 재고·현금·납기·수요가 어떻게 변하는가. 계산만 한다.
2. **판단 (LLM):** 주어진 관측값에서 그 사람이 무엇을 확인하고 무엇을 고르는가. 이번에 검증하는 부분이다.
3. **학습 갱신:** 결과를 보고 다음 기준이 바뀌는가. 인터뷰 약사는 "데이터가 안 쌓였다"고 말했으므로 중요한 변수지만, 인터뷰 1건으로는 검증할 수 없다. 재인터뷰가 필요하다 (이번 PoC 범위 밖).

**공공/민간 데이터의 역할은 "장면 입력"이다.** 환경이 얼마나 현실적인지(환경 타당성)는 올려 주지만, 이 사람이 이렇게 판단하는지(판단 타당성)는 올려 주지 않는다. 판단 타당성은 인터뷰와 약사 본인 응답으로만 올라간다.

## 3. 어떻게 하는가

### 3.1 역할 분담

| 주체 | 하는 일 | 하지 않는 일 |
|---|---|---|
| 코드 | 관측값 생성, 실물 확인 결과 공개, 입고·재고·약정·채무 계산, 제약 검사 | 약사의 성향이나 규칙 우선순위를 정함 |
| LLM | 관측값을 보고 `실물확인` / `후보 확정(보류·5팩·10팩 등)` / `판단 유보` 중 하나를 고르고, 근거 ID와 누락 정보를 제시 | 숨은 상태 접근, 수치 기준 창작 (4장 참조) |
| 실제 약사 | AI 답을 보기 **전에** 자기 답을 먼저 줌 (첫 행동, 허용 범위, 우선조건 2개, 필요 정보, 장면 현실성) | — |

- `보류(Q_0)`는 "주문하지 않기로 확정"이고, `판단 유보(defer)`는 "정보가 부족해 결정하지 않음"이다. 구분해서 기록한다.
- LLM이 고르지 않은 행동을 코드가 대신 실행하거나, 한도를 넘는 주문을 자동으로 깎지 않는다. 오류로 돌려 다시 고르게 한다.

### 3.2 정보의 층 (섞지 않는다)

| 조건 | 넣는 것 | 알려 주는 것 |
|---|---|---|
| B1 | 같은 환경·제약, 개인 근거 없음 (일반 약사 LLM) | 기준선. 개인 자료 없이도 맞히는 정도 |
| P0 | B1 + 인터뷰 근거(claims·rules·cases, ID로 검색) | 인터뷰의 기여 = P0와 B1의 차이 |
| P1 | P0 + 공공/민간 데이터를 장면 입력으로 | 환경 현실성의 기여 (약사에게도 같은 정보를 준다) |
| P2 | P1 + 다른 약사 데이터 ("타 약사 유래" 표시) | 동료 사전지식의 기여. 인터뷰가 늘어난 뒤 |
| B0 (선택) | 실행 가능한 기존 규칙만 코드화. 우선순위 미정이면 판단 유보 | 규칙 구현을 넘는 기여 |

- 이번 PoC에서는 **B1과 P0**부터 비교한다. P1은 장면 입력이 연결된 뒤, P2는 인터뷰가 늘어난 뒤 추가한다.
- 층을 분리하면 답변마다 어느 층에서 나온 정보인지 남는다. 인터뷰 약사의 근거는 Layer 0(P0)로 ID와 함께 추적된다.
- 층을 합치면 "그 약사"가 아니라 "개업 초기 약사 일반"이 되어, 인터뷰 약사와 대조해도 무엇 덕분에 맞았는지 알 수 없다.

### 3.3 시나리오 카드

카드는 두 종류다. **평가에 쓰는 것은 2종뿐이다.**

| 종류 | 설명 | 용도 |
|---|---|---|
| 1종: 인터뷰 안의 상황 | 인터뷰에서 이미 다룬 상황의 재구성 (예: 슬라이스 1 후보 SC01은 휴진 X003, 현금 부담 E034, 도매 품절 I06이 모두 인터뷰 안에 있다) | 시연, 일관성 점검, 개발용. **평가에 쓰지 않음** |
| 2종: 인터뷰 밖의 인접 상황 | 인터뷰에 없던 상황이되, 인터뷰의 규칙이 원리상 적용될 수 있는 상황 | **평가용** |

2종 카드의 조건:
- 인터뷰와 완전히 무관한 상황이면 검증이 아니라 외삽 시험이다. 인접성을 표시하고, 무관한 상황은 따로 분류한다.
- 법 준수처럼 어떤 약사라도 같은 답을 하는 상황은 변별력이 낮다. **재량이 갈리는 지점**을 고른다.
- 절대 수량(5팩 vs 10팩)보다 **상대 판단**(더 사나 덜 사나, 무엇을 먼저 보나, 조건을 바꾸면 어느 방향으로 변하나)을 묻는다. 임의 수치에 덜 의존한다.
- 약사와 페르소나에게 **같은 카드, 같은 정보**를 준다. 한쪽만 아는 정보가 있으면 차이의 원인을 알 수 없다.
- 모든 수치는 "가상"이다. 후보 밖 답변도 받고, 오답으로 강제하지 않는다.
- **약사의 답을 claims에 추가하면 그 카드는 개발용으로 전환**한다 (HANDOFF §1의 "새 답변은 새 근거"와 같은 규칙). 정확도 확인에는 새 카드를 쓴다.

2종 후보 (인터뷰가 이미 다룬 범위와 대조한 뒤 확정할 것): 긴 연휴 전 발주, 유효기간 임박·보관 공간 부족, 반품 불가 신제품 입점 제안, 인근 신규 약국 개업.

### 3.4 한 번의 판단 흐름

1. 코드가 **관측값만** 만든다 (판단 시각, 재고 출처와 관측 여부, 현금, 납기, 기존 미입고, 후보 수량).
2. LLM이 `실물확인 / 후보 확정 / 판단 유보` 중 하나를 고른다.
3. `실물확인`이면 코드가 확인 결과를 공개하고, **갱신된 관측값으로 다시 판단**한다. 같은 확인의 반복 요청은 종료한다.
4. `후보 확정`이면 코드가 제약을 검사하고 이후 3일을 한 번 계산한다.
5. 화면에는 **실제 일어난 조회 순서**를 기록으로 보여 준다. 모델이 쓴 설명은 "제시한 이유"일 뿐 내부 사고과정이 아니다.

### 3.5 비교와 측정

- **약사 5답:** 첫 행동, 허용 수량 범위, 우선조건 2개, 필요한 추가 정보, 장면의 현실성.
- **변화 방향 일치:** 같은 카드에서 조건 하나만 바꿨을 때, 약사와 페르소나가 같은 방향으로 바뀌는가. 현금과 납기를 한 번에 하나씩, 2×2로 본다.
- **본인 재응답:** 시간을 두고 같은 카드를 약사에게 다시 준다. 약사 본인도 답이 바뀌므로, 모델 일치율은 이 **사람 쪽 상한**에 비춰 읽는다.
- **반복과 흔들림:** 같은 입력을 독립 3회 돌리고, 문장·선택지 순서만 바꾼 검사도 한다. "3번 중 2번 주문"은 관찰 횟수이지 67% 신뢰도가 아니다.
- **사전 통과 기준:** 결과를 보기 전에 "무엇이 나오면 재현한다/못 한다"를 정해 둔다. 응답자 1명·카드 소수이므로 통계 추론이 아니라 **진단**으로 쓴다. 기준은 9장에 미결로 남겼다.
- **발주 장면의 한계 (알고 쓸 것):**
  - 단일 품목·3일은 최소 장면이다. 현금 제약은 품목 간 예산 배분에서 작동하는데 1품목에는 그 선택이 없다.
  - 결제일이 관찰기간 밖이고 반품·유효기간이 계산에서 빠지면, 인터뷰 약사가 대량 발주를 꺼리는 실제 이유(그달 결제 부담, 반품 곤란, 유효기간, 예측 불가: E034, E038)가 사라져 **많이 사는 쪽이 항상 유리해 보인다.**
  - 그래서 비교 화면에 미충족수요뿐 아니라 **기말재고 금액과 월 결제 예정액**을 같은 비중으로 보여 준다.

### 3.6 니즈 카드

판단 재현 평가와 **분리**해서 만든다. 니즈를 찾는 쪽으로 페르소나를 조정하면 해결책 편향이 재현 점수에 섞인다.

| 칸 | 내용 |
|---|---|
| 상황 | 어떤 상황인가 (근거 ID) |
| 현재 하는 방식 | 지금 어떻게 대처하는가 (실물 확인, 최소 주문 등) |
| 어려움 | 약사가 **자발적으로** 말한 것인지, 인터뷰어 제안에 대한 반응인지 표시 |
| 영향·빈도 | 결과(품절 손해, 현금 부담 등)와 얼마나 자주 |
| AX 여지 | **가설** 표시와 근거 수준 |
| 도입 조건 | 수용 조건과 거부 조건 (동의, 시간, 비용, 신뢰, 법적 경계) |
| 확인 상태 | 약사가 확인했는가 |

- 인터뷰에서 어려움이 나온 근거: 반품 곤란(E038), 개업 초기 현금 부담(E034), 전산보다 실물 확인이 빠름(E030), 수요 예측 불가.
- 인터뷰어가 해결책을 먼저 제안한 대목에 대한 반응(`제안 반응`, 예: I12, I13)은 수요 증거로 약하다. 대신 **수용·거부 조건**의 근거로 쓴다.
- 약사에게 확인할 때는 해결책을 보여 주기 **전에** 어려움의 빈도·심각도·현재 대처를 먼저 받고, 그다음 도입 조건을 묻는다.
- 시뮬레이션이 띄울 수 있는 것은 가설 후보다. 예: 페르소나가 반복해서 실물 확인을 요청하면 전산 신뢰 부족의 가능성이 있다. 이를 약사가 확인하기 전에는 니즈로 쓰지 않는다.

## 4. LLM이 하면 안 되는 것

| # | 금지 | 이유·근거 |
|---|---|---|
| 1 | 숨은 실물 재고, 미래 수요, 선택별 결과, 정답에 접근하거나 요청하기 | 정보 누출. 모델에는 관측값만 준다 |
| 2 | 인터뷰·CSV에 없는 수량·비율·임계치를 만들기 (예: "1.5일 미만이면 긴급", "8~9일분") | G02. 이 값들은 가정(`assumption`)이다 |
| 3 | 규칙 사이의 우선순위를 임의로 완성하기 | 인터뷰로 정해지지 않은 순서를 성향으로 확정하게 된다 |
| 4 | 시뮬레이션 출력을 사실로 말하거나 claims·근거로 되먹이기 | G04 |
| 5 | 약사 2인의 합의·권한·성향을 확정하기 | G07 |
| 6 | 과거 직장·타약국 경험을 현재 약국의 판단으로 단정하기 | G01 |

## 5. 결과를 읽는 법

**검증 종류를 하나의 "검증 완료"로 합치지 않는다.**

| 종류 | 무엇을 확인하나 | 현재 상태 |
|---|---|---|
| 구조 점검 | ID·열·코드 연결 (`validate.py` 8가지) | 통과 |
| 계산 검증 | 재고·입고·약정·채무 계산이 맞는가 | 팀 참조 코드 테스트 16개 통과 보고 (우리가 실행해 확인하지는 못함) |
| 판단 재현 | 약사 답과 비슷한가 | 미실행 |
| 니즈 확인 | 약사가 어려움을 확인했는가 | 미실행 |

- 계산 검증 통과는 페르소나 정확도를 뜻하지 않는다.
- 화면에는 항목마다 `인터뷰 / 가정 / 미확인`을 함께 표시한다.
- HANDOFF의 결정 카드에는 "확신도"가 있다. 수치 확신도는 모델의 자기평가라 보정되지 않았으므로, **수치 대신 "근거 수준과 누락 정보"로 바꾸거나 "모델 자기평가(보정 안 됨)"로 표기**하는 것을 권한다 (9장).

## 6. 돌린 뒤 할 일

1. **약사 응답 수집:** 5답을 AI 답 공개 전에 받는다. 응답은 개발용/평가용 구분과 함께 기록한다.
2. **방향 일치 확인:** 조건을 바꿨을 때 변화 방향이 같은지 본다. B1과 P0를 같이 본다.
3. **본인 재응답으로 상한 보정:** 일정 간격 뒤 같은 카드를 다시 받는다.
4. **니즈 카드 확인:** 약사가 어려움의 빈도·심각도·대처를 확인하고, 그다음 도입 조건을 답한다.
5. **확장 준비:** 일정 기간 뒤 재인터뷰(학습 단계)와 추가 인터뷰(유형 확장). 인터뷰가 늘면 P2를 켜고, 유형 검증은 "여러 약사 응답의 분포 안에 들어오는가"로 바꾼다.
6. **가능하면 앞으로의 실제 행동과 비교:** 페르소나의 예측을 미리 기록해 두고 나중에 실제 주문과 비교한다. 동의와 데이터 접근이 필요하므로 선택 사항이다.

**기록 규칙:** 약사의 새 답변은 관측이므로 claims에 추가할 수 있다. 시뮬레이션 로그는 어떤 경우에도 claims에 넣지 않는다.

## 7. 담당자의 우려·질문과 현재 판단

| 우려·질문 | 현재 판단 |
|---|---|
| 층을 분리하면 인터뷰 약사의 근거가 희미해지지 않나 | 섞을 때만 희미해진다. 분리하면 Layer 0로 추적된다. 다만 목표를 유형으로 바꾸면 인터뷰 약사는 "씨앗 사례"가 된다 |
| 개업 3주차 약사 1명은 많은 약사를 대변하기엔 파이가 작다 | 맞다. 그래서 지금은 개인 재현으로 한정하고, 유형은 인터뷰를 늘려 확장한다 |
| 최종 목적을 "인근에 의원이 있는 동네약국 운영자 유형"으로 해도 되나 | 타당하다. 유형을 측정 가능한 변수(인근 의원 수·진료과·같은 건물 여부·처방 의존도)로 정의해야 하고, 인터뷰 약사는 그 축의 한 점이다. 이 정의에 공공 데이터가 쓰인다 |
| 대상이 결국 "개업 3주차 약사"뿐이라는 우려 | 시뮬레이션을 "조건이 바뀔 때 판단이 어떻게 바뀌는가"로 정의하면 한 사람 대상으로도 성립한다 |
| 타 약국 경력이 있어 전문성은 높다고 봐도 되나 | 전문성의 배경으로는 괜찮다. 단 과거 경험으로 표시하고(G01), 전문직 규범 판단은 B1도 맞히므로 P0의 차별점은 **재량적·개인 특유의 선택**에서 나온다 |
| 시나리오는 인터뷰에 없던 상황이어야 하지 않나 | 그렇다. 평가용은 2종 카드뿐이다. SC01처럼 인터뷰 안의 요소로 구성된 카드는 시연·개발용이다 |
| 공공/민간 데이터로 근거 신뢰도를 높이는 것 | 환경 타당성을 올린다. 판단 타당성은 올리지 못한다. 약사와 페르소나에게 같은 정보를 줘야 한다 |
| 다른 약사 데이터를 근거로 넣어야 풍부해지지 않나 | 별도 층(P2)으로 넣는다. 섞으면 개인 재현을 평가할 수 없다 |
| "개업 3주차 약사 재현"에 집중해도 주제에서 벗어나지 않나 | 벗어나지 않는다. 현재 근거로 주장할 수 있는 유일한 범위다. 문서에는 "대변"보다 "개인 재현도"로 쓴다 |
| 니즈와 AX 도입 여지도 보여야 한다 | 니즈 카드로 분리한다. 증거는 인터뷰의 자발적 어려움과 실제 대처이고, 시뮬레이션은 가설 후보만 낸다 |

## 9. 아직 정해지지 않은 것

- 대변 범위 문구의 최종 표현 ("개인 재현도"로 통일할지).
- **사전 통과 기준:** 무엇이 나오면 재현한다/못 한다고 볼지, 카드 수, 반복 횟수. (HANDOFF §6의 `tolerance_pct`와 별개의 문제)
- 결정 카드의 "확신도"를 어떻게 바꿀지.
- 2종 카드의 확정 목록 (인터뷰가 다룬 범위와 대조 필요).

- 앞으로의 실제 주문과 비교할 수 있는지 (동의, 데이터 접근).
- 유형 정의 변수와, 추가로 몇 명을 인터뷰할지.
- **이번 PoC에서 보여 줄 최소 범위(제안):** 시나리오 카드 1~2장, AI 답 대 약사 답 비교 화면, 범위 문구, 정보 조회 기록. 학습 갱신과 유형 확장은 로드맵으로만 제시한다.
